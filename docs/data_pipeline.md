# The data pipeline, step by step

This walks through exactly what happens between "raw data somewhere" and
"a chunk with an embedding, ready to be retrieved" — the three stages
`rag_support.rag.pipeline.run_ingest_clean_embed()` runs in sequence
(`rag-support pipeline`, or `POST /ingest`).

## Stage 0: where the data comes from

`rag_support/data/sources/base.py` defines one interface:

```python
class DataSource(ABC):
    name: str
    def fetch(self) -> Iterator[RawRecord]: ...
```

Two implementations satisfy it:

### `LocalSampleSource` (`DATA_SOURCE=sample`, the default)

Reads `src/rag_support/data/sample_dataset/support_kb_raw.jsonl` — 80
records covering 9 categories × 36 intents for a fictional SaaS product,
"Northwind Cloud." It's generated by `scripts/generate_sample_dataset.py`,
which is worth reading directly; the short version:

- Each intent (e.g. `BILLING`/`cancel_subscription`) has a hand-written
  canonical answer and 2-3 paraphrased customer questions.
- **~15% of records are deliberately corrupted** — wrapped in stray HTML
  tags, given doubled whitespace, flipped to inconsistent casing, or HTML-
  entity-escaped — the kind of mess a real support-ticket export actually
  contains. This exists so the cleaning stage (below) has real,
  verifiable work to do instead of running against already-pristine text.
- **6 exact duplicates are injected** on top of that, simulating the same
  canned answer being logged more than once.

This makes the sample dataset a legitimate, if small, stand-in for messy
real-world data — not a toy "the pipeline trivially always passes" fixture.
Regenerate it with `python scripts/generate_sample_dataset.py` if you want
to extend it (add entries to the `KB` list in that file).

### `HuggingFaceSource` (`DATA_SOURCE=hf`)

Streams `bitext/Bitext-customer-support-llm-chatbot-training-dataset` (~27k
rows: `instruction`, `category`, `intent`, `response`) from the Hugging
Face Hub via the `datasets` library, mapping each row to the same
`RawRecord` shape `LocalSampleSource` produces. This is the "production"
path — real network access to `huggingface.co` required.

**This project's own build/CI environment doesn't have that access** (a
sandboxed container with an explicit network allowlist that includes
`pypi.org` and `github.com` but returns `403 Forbidden` for
`huggingface.co` and `datasets-server.huggingface.co` — verified directly
with `curl -I` before any code was written, not assumed). `HuggingFaceSource`
is fully implemented and was never runnable from inside that environment to
test live; if it hits the same wall in yours, its `fetch()` raises a
`RuntimeError` that says exactly that and tells you to set
`DATA_SOURCE=sample`. See [architecture.md](architecture.md) for the full
reasoning behind treating this as a real constraint to design around
rather than a gap to gloss over.

## Stage 1: ingestion (`data/ingest.py::run_ingestion`)

Drains a `DataSource` into the `documents` table via
`storage/repository.py::bulk_insert_documents`, batching inserts (default
200 records/batch) rather than one `INSERT` per row. Every row starts with
`status="ingested"`. Nothing is deduplicated or cleaned at this stage —
that's stage 2's job, deliberately kept separate so ingestion stays a
dumb, fast, always-safe-to-re-run "get the raw data into the database" step.

```bash
rag-support ingest
# INFO Ingestion complete: source=sample records_read=80 documents_written=80
```

## Stage 2: cleaning (`cleaning/pipeline.py::run_cleaning`)

Operates on every `documents` row with `status == "ingested"`. For each:

1. **Normalize** (`cleaning/normalize.py::clean_text`) — strip HTML tags
   and unescape entities (via BeautifulSoup), Unicode NFKC-normalize,
   sentence-case lines that are almost entirely uppercase, collapse
   whitespace (including per-line trailing/leading whitespace — a real bug
   caught by the test suite where a naive "collapse runs of spaces" regex
   left a trailing space before a newline that a *stricter* per-line strip
   catches).
2. **Quality filter** (`is_low_quality`) — reject near-empty or
   punctuation-only text before it ever gets chunked or embedded.
3. **De-duplicate** (`content_hash` + `content_hash_exists`) — hash the
   *cleaned* text (not the raw text) and check it against every
   already-cleaned document's persisted hash. Hashing the cleaned text is
   what makes two records that differ only in HTML wrapping, whitespace, or
   casing collapse to the same hash and get caught as duplicates — exactly
   what the sample dataset's injected noise is designed to test. The hash
   is persisted (`documents.content_hash`, indexed), so this works across
   separate pipeline runs, not just within one batch.
4. **Chunk** (`cleaning/chunker.py::chunk_text`) — sentence-aware packing
   into ~`CHUNK_SIZE`-word windows (default 800) with `CHUNK_OVERLAP`-word
   overlap (default 120), measured in words rather than a model-specific
   token count (a documented simplification — see the module docstring for
   why: no tokenizer-vocab download dependency, ~30% accuracy vs. true
   token count, which is enough precision for choosing a chunk boundary).
   Whole sentences are packed greedily; a single sentence longer than
   `CHUNK_SIZE` still gets its own chunk rather than being truncated.

```bash
rag-support clean
# INFO Cleaning complete: seen=80 cleaned=74 duplicates=6 low_quality=0 chunks=74
```

Every rejected document keeps its row (`status="rejected_duplicate"` or
`"rejected_low_quality"`) rather than being deleted — the pipeline's
decisions stay auditable.

## Stage 3: embedding (`embeddings/pipeline.py::run_embedding`)

Finds every `document_chunks` row with `embedding IS NULL`
(`get_chunks_missing_embeddings`), embeds it in batches (default 64) with
whichever `EmbeddingProvider` is configured, and writes the vector back
along with which provider produced it (`embedding_provider` column — so a
corpus embedded partly by one tier and partly by another, e.g. after a
provider config change, is distinguishable after the fact).

```bash
rag-support embed
# INFO Embedded 64 chunks so far (provider=offline)
# INFO Embedded 74 chunks so far (provider=offline)
```

See [architecture.md](architecture.md) for what the three embedding tiers
actually are and how `auto` mode picks between them.

## Running it all together

```bash
rag-support pipeline
```

is exactly `run_ingestion` → `run_cleaning` → `run_embedding` called in
sequence inside one database session
(`rag_support/rag/pipeline.py::run_ingest_clean_embed`) — the "single
cohesive pipeline" the project set out to build, not three scripts a human
has to remember to run in the right order.
